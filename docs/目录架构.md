# SpringHere CLI 目录架构

> 状态：与当前仓库一致，描述「现在有什么、各自做什么」
>
> 仓库：`springhere/`（模块 `github.com/buding00/springhere`）
>
> 相关文档：[CLI实施方案最终.md](CLI实施方案最终.md)（目标与流水线）；仓库根 [README.md](../README.md)（使用者说明）

本文只讲 **CLI 仓库自己的目录**。Gin 后端与 React 前端的业务源码不在本仓库，生成时按注册表从 GitHub / Gitee（或本地目录）拉取。

## 1. 在整体里的位置

工作区里三份独立仓库，职责分开：

```text
gingen/
├── springhere/                 本仓库：脚手架 CLI，不内嵌前后端源码
├── springhere-gin-server/      后端模板源（GitHub buding00 / Gitee lovebuding）
└── springhere-react-admin/     前端模板源（同上）
```

本仓库负责：问用户要什么、校验组合是否已验收、拉取模板、按契约拷文件并改几处标识、写出根级编排，然后原子落到目标目录。

不负责：实现登录/用户接口、维护前端页面、在生成时执行 `go mod tidy` / `pnpm install`。

## 2. 顶层目录

```text
springhere/
├── cmd/springhere/             可执行入口，只有 main
├── internal/                   全部实现（不对外 import）
│   ├── command/                Cobra 命令、退出码
│   ├── prompt/                 交互问答
│   ├── registry/               解析并校验内嵌组件表
│   ├── embedded/               go:embed：组件表 + 组合根文件
│   ├── source/                 本地目录 / git archive / 镜像选择
│   ├── contract/               组件仓库的 .springhere-template.yaml
│   ├── initializer/            拷贝、转换、根文件、清单
│   ├── safefs/                 路径边界、白名单拷贝、staging 提交
│   ├── validate/               项目名、module、来源、输出目录
│   ├── selfupdate/             从 GitHub Release 下载并替换当前二进制
│   ├── clierr/                 带退出码的错误
│   └── version/                CLI 版本字符串
├── testdata/                   缩小的假 backend / frontend，给单测用
├── docs/                       方案与架构说明（本文所在目录）
├── .github/workflows/          Release 编译上传；GitHub → Gitee 镜像备份
├── Makefile                    本仓库的 build / test / vet
├── go.mod / go.sum
└── README.md                   给使用者的安装与 `springhere new`
```

和方案文档第 9 节的示意相比，当前实现把 `components.yaml` 和 `combinations/` **放进 `internal/embedded/`**，用 `go:embed` 打进二进制；没有单独的顶层 `registry/`、`combinations/`、`integration/`。

## 3. 入口与构建

| 路径 | 作用 |
|---|---|
| `cmd/springhere/main.go` | 调用 `command.Execute()`，失败则 `command.Exit` |
| `Makefile` | `build` 产出 `bin/springhere`；`test` / `vet` / `fmt` 只覆盖本仓库 |
| `go.mod` | 模块路径与依赖：Cobra、survey、`golang.org/x/mod`、yaml.v3 |

编译后的二进制里已经带上组件注册表和 `gin-react-admin` 的根级文件，运行 `springhere new` **不需要**再读本仓库的源码树。

## 4. `internal/` 各包

按一次 `springhere new` 的调用顺序：

```text
command → prompt / validate / registry
       → initializer
            → source（取模板）
            → contract（读契约）
            → safefs（白名单拷到 staging）
            → initializer 自己的 transform / 根文件 / manifest
            → safefs.Commit（rename 到目标）
```

### `command/`

Cobra 根命令与子命令。

| 文件 | 作用 |
|---|---|
| `root.go` | `springhere` 根命令、`version`、统一退出 |
| `new.go` | `springhere new`：收集 flag / 交互结果，交给 `initializer.Run` |
| `update.go` | `springhere update`：从 GitHub Release 下载并替换当前二进制 |
| `root_test.go` | 命令层测试 |

`new` 认识的参数：`--backend`、`--frontend`、`--module`、`--source`、`--backend-template-dir`、`--frontend-template-dir`、`--output`、`--dry-run`、`--no-git`、`--yes`。`update` 认识 `--yes`、`--check`、`--version`，没有 `--source`。这里不碰模板文件系统细节。

### `prompt/`

类 Vite 的问答。TTY 才进入交互；非 TTY 且没有 `--yes` 会在 command 层直接失败。选项列表来自 registry（后端 / 前端 id、源），不写文件。

### `registry/`

把 `embedded.ComponentsYAML` 解析成结构并校验：

- 组件必须有 github 或 gitee 源，且 `url` + `ref` 齐全
- 同一组件两边的 `commit` 要么都空（跟 ref tip），要么都填且相同
- `combinations` 必须引用已有 backend / frontend；`tested=false` 拒绝生成

不负责 git 拉取。组件「拉哪一版」完全由内嵌 yaml 的 `ref` / `commit` 决定，运行时不能改。

### `embedded/`

唯一允许把静态文件打进二进制的包。

```text
internal/embedded/
├── embedded.go                 //go:embed components.yaml 与 combinations/
├── components.yaml             官方组件与组合登记
└── combinations/
    └── gin-react-admin/        生成项目根上的说明，不是业务源码
        └── README.md
```

`components.yaml` 当前登记 `gin` + `react`，组合 `gin-react-admin`（`tested: true`）。GitHub / Gitee 的 `ref` 是 `main`，`commit` 为空，表示跟分支 tip（详见仓库里对该文件的注释）。

`combinations/gin-react-admin/` 只会写到生成项目的**根目录 README**。Compose、Nginx 来自后端模板的 `deploy/springhere/`，生成时 `deploy_stack` 会改成 `<项目名>_backend/deploy/<项目名>/`。前后端的 `AGENTS.md` 随组件契约拷入，并改写其中的 module 路径、compose 目录和品牌词。占位符 `__PROJECT_NAME__`、`__BACKEND_DIR__`、`__FRONTEND_DIR__` 等只在组合 README 里替换。

### `source/`

模板从哪来。

| 文件 | 作用 |
|---|---|
| `resolve.go` | 本地目录优先；否则按 `--source` 选镜像并 `FetchGit` |
| `detect.go` | `auto` 时测 `github.com:443` / `gitee.com:443` 延迟 |
| `git.go` | 临时 bare 仓、`fetch --depth 1 --no-tags`、`git archive` 解树 |
| `git_test.go` | 用本地 git fixture 测拉取与 commit 校验 |

`commit` 非空则必须与 `rev-parse` 结果一致，否则失败。为空则接受该 `ref` 当前 tip，并把实际 SHA 交给后续清单。拒绝 archive 里的 symlink / 硬链 / 未知文件类型。

### `contract/`

读取模板根目录的 `.springhere-template.yaml`：

- `component` 必须是 `backend` 或 `frontend`
- `payload.include` 是拷贝白名单（相对路径，禁止 `..` 和绝对路径）
- `transforms` 第一版只允许 `go_module`、`json_string`、`yaml_scalar`

`cli_constraint` 字段会解析进结构体，**当前不拿来和 CLI 版本比较**。缺这个文件会提示：远程请先推到对应 ref，本地请把 `--*-template-dir` 指到组件仓库根。

### `initializer/`

生成流水线的中枢，只在 **staging 临时目录** 里工作。

| 文件 | 作用 |
|---|---|
| `initializer.go` | `Run`：解析源 → 读契约 → 拷白名单 → transform → 写组合 README → 写清单 →（非 dry-run）提交 |
| `structured.go` | JSON 字符串字段、YAML 标量 |
| `deploy.go` | `deploy_stack`：重命名 `deploy/<from>` 并改 compose 的 `container_name` |
| `brand.go` | `app_brand`：把前端配置里的品牌词换成项目名，并改 `mark` |
| `gomodule.go` | 改 `go.mod` 的 module 路径，并用 AST 改 Go import 前缀 |
| `manifest.go` | 写出 `.springhere.yaml`（CLI 版本、源 URL、ref、实际 commit、契约摘要） |
| `initializer_test.go` | 用 `testdata/` 跑本地生成 |

失败时删 staging，目标目录保持原样。dry-run 只打印将创建的路径。提交成功后在 `<项目名>_backend/`、`<项目名>_frontend/` 分别 `git init`（`--no-git` 跳过），失败只警告。根目录不建 Git 仓库。

### `safefs/`

所有落盘路径都经过这里。

| 文件 | 作用 |
|---|---|
| `path.go` | 排除 `.git`、`node_modules`、`.env`（保留 `.env.example`）等 |
| `copy.go` | 按 `payload.include` 白名单拷贝，拒绝 symlink |
| `commit.go` | 目标必须不存在或为空；`rename` staging → 目标 |
| `safefs_test.go` | 路径与拷贝边界 |

不在拷贝过程中直接写最终目录。

### `validate/`

纯规则：项目名（小写 + 数字 + 连字符）、Go module 路径、`--source` 取值、输出目录。command 和 initializer 都会用。

### `selfupdate/`

`springhere update` 的实现。列 GitHub Release、按 semver 取最高稳定版（或 `--version` 指定）、下载资产、校验 `checksums.txt`、解压、替换 `os.Executable()` 指向的文件。

不访问 Gitee，不 `git clone`，不在用户机器上 `go install`。匿名调用 GitHub API；遇到限流可设环境变量 `GITHUB_TOKEN`。

### `clierr/`

带退出码的错误类型，供 `command.Exit` 映射：

| 码 | 含义 |
|---|---|
| 2 | 参数 / 用法 |
| 3 | 未知组件 |
| 4 | 组合未验收或不存在 |
| 5 | 契约非法 |
| 6 | 源解析失败 |
| 7 | 目标冲突 |
| 8 | git 失败 |
| 1 | 未分类内部错误 |

### `version/`

`Version` 默认 `0.1.0`，Release 工作流和 `make build VERSION=...` 用 ldflags 覆盖。用于 `springhere version`、生成项目里的 `cli_version`，以及 `update` 比较当前版本。**不**用来选择前后端 tag。

## 5. `testdata/`

给 `initializer` / `contract` 等单测用的微型模板，不是可运行的产品：

```text
testdata/
├── backend/
│   ├── .springhere-template.yaml
│   ├── go.mod
│   ├── application.yaml
│   ├── cmd/main.go
│   └── internal/pkg/...
└── frontend/
    ├── .springhere-template.yaml
    ├── package.json
    └── src/index.ts
```

契约形状与真实组件仓库相同（include + transform），体积小、不访问网络。测远程 git 时用临时本地仓库当 fixture，也不依赖 GitHub。

## 6. `docs/` 与 CI

| 路径 | 作用 |
|---|---|
| `docs/CLI实施方案最终.md` | 第一版 CLI 的范围、安全约束、注册表与流水线设计 |
| `docs/目录架构.md` | 本文：当前目录与包职责 |
| `.github/workflows/release.yml` | 推送 `vX.Y.Z` tag（或手动指定 tag）时交叉编译并上传 GitHub Release |
| `.github/workflows/sync-to-gitee.yml` | `--mirror` 同步到 `https://gitee.com/lovebuding/springhere.git`；GitHub 为开发源 |

`release.yml` 用默认 `GITHUB_TOKEN`，不必另加 Secret。`sync-to-gitee.yml` 需要 `GITEE_TOKEN`，只备份 git 对象，不给 Gitee 传二进制。`update` 只读 GitHub Release。

## 7. 生成项目长什么样（对照本仓库）

`springhere new my-app` 成功后，目标目录来自三处，而不是「把本仓库拷过去」：

```text
my-app/
├── my-app_backend/       ← gin-server，含 deploy/<项目名>/docker-compose.yaml 与 nginx.conf
├── my-app_frontend/      ← react-admin
├── README.md             ← 本仓库 embedded/combinations/gin-react-admin/
└── .springhere.yaml      ← initializer 现场写的生成记录
```

`<项目名>_backend/` 与 `<项目名>_frontend/` 各自 `git init`。因此：改登录接口和 Compose/Nginx 去 `springhere-gin-server` 的 `deploy/springhere/`；改页面去 `springhere-react-admin`；改根 README 去本仓库的 `internal/embedded/combinations/`；改「拉哪一版、哪两个源」去 `internal/embedded/components.yaml`（改完需重新编译安装 CLI）。

## 8. 包边界（当前实现）

| 包 | 做 | 不做 |
|---|---|---|
| `command` | 参数、help、退出码 | 读契约、写模板文件 |
| `prompt` | 问答；选项来自 registry | 写文件 |
| `registry` | 组件与 combination 合法性 | 拉取 Git |
| `embedded` | 提供内嵌字节与 FS | 解释 yaml 语义 |
| `source` | 本地目录或 git archive（给 `new`） | 更新 CLI 自身 |
| `selfupdate` | GitHub Release、校验、替换当前二进制 | Gitee、本机编译、升级已生成项目 |
| `contract` | schema、白名单、未知 transform 拒绝 | 执行 transform |
| `initializer` | 转换、写根 README、写清单、在 `<项目名>_backend` / `<项目名>_frontend` `git init` | 跑 `go test` / `pnpm`、根目录建 Git 仓库 |
| `safefs` | 排除规则、白名单拷贝、原子 rename | 改 go.mod / JSON / YAML 内容 |
| `validate` | 名字与路径规则 | I/O |
| `clierr` | 错误与退出码 | 业务判断 |
| `version` | CLI 版本字符串 | 组件 tag 映射 |

以后加第二种后端（例如 Axum）时，预期新增的是 `initializer` 下的语言转换和 `embedded/combinations/` 里另一套根文件，而不是改 `safefs` 或重写 `new`。
